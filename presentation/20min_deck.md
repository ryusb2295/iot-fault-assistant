# IoT 통신 장애 감지와 대응 보조 시스템

20분 발표 구성안 · 대상: 개발·평가 심사자 · 시연 환경: PC MQTT 시뮬레이터, FastAPI, SQLite, Vue, 로컬 Ollama

## 1. 문제와 목표 (1분)

- 장치 메시지가 멈추거나 늦거나 형식이 잘못되면 운영자가 원인 후보와 확인 순서를 빠르게 파악해야 한다.
- 목표: MQTT 수신 → 규칙 판정 → 장애 기록 → 근거 문서 기반 점검 안내 → 사용자 조치 기록.

발표: AI는 장애를 판정하지 않는다. 장애 유형과 복구 여부는 규칙 엔진과 수신 로그가 결정한다.

## 2. 범위와 시연 환경 (1분)

- 감시 대상: RPI-01 한 대. PC MQTT 시뮬레이터로 재현한다.
- 발표용 SQLite는 개발 DB와 별도로 시작한다.
- Raspberry Pi 코드와 설정은 준비됐지만 실제 Pi Ethernet 단절 실험은 이번 측정에 포함되지 않았다.

## 3. 시스템 구조 (2분)

`PC 시뮬레이터 → MQTT Broker → Python Worker → 규칙 엔진 → SQLite → FastAPI → Vue`

AI 경로: `장애 상세 → 유형별 매뉴얼 절 검색 + 연결 로그 → Ollama → 점검 안내 + 출처`

발표: Worker가 수신과 판정을 맡고 API는 저장된 상태를 조회한다. AI 호출은 장애 상세에서만 수행한다.

## 4. 세 가지 장애 판정 (2분)

| 유형 | 판정 기준 | 관찰할 화면 |
| --- | --- | --- |
| 통신 중단 | 마지막 유효 상태 수신 후 10초 이상 미수신 | 통신 상태와 새 장애 |
| 응답 지연 | 요청 후 약 3초가 지나도 응답 없음 | 요청·응답 로그와 지연 이벤트 |
| 형식 오류 | 유효하지 않은 MQTT 메시지 | 검증 오류 로그와 장애 유형 |

발표: 복구 여부와 사용자 조치 완료 여부는 독립적으로 관리한다.

## 5. 데이터 모델과 운영 화면 (1.5분)

- `devices`: 현재 상태와 마지막 수신.
- `communication_logs`: 수신 메시지와 검증 결과.
- `fault_events`: 장애 유형, 탐지·복구 시각.
- `action_records`: 체크리스트와 사용자 조치.

화면 시연: 대시보드의 장애 유형별 건수, 복구/미복구, 조치 완료/미완료를 확인한다.

## 6. 실시간 시연 (3분)

1. 발표용 빈 DB와 시스템을 시작한다.
2. 정상 메시지 수신을 확인한다.
3. 시뮬레이터를 장애 모드로 전환해 새 이벤트를 확인한다.
4. 장애 상세에서 로그와 매뉴얼을 확인한다.
5. 정상 모드로 복귀해 복구 시각을 확인한다.

대체: 실시간 연결에 실패하면 `presentation/video/`의 실제 MQTT 시연 영상을 재생한다.

## 7. 규칙 기반 탐지 실험 15회 (2분)

| 유형 | 시행 | 탐지 시간 평균 | 범위 |
| --- | ---: | ---: | ---: |
| 통신 중단 | 5회 | 10.106초 | 10.003~10.207초 |
| 응답 지연 | 5회 | 3.190초 | 3.010~3.269초 |
| 형식 오류 | 5회 | 측정 불가 | 수신·판정 시각 해상도 동일 |

발표: 통신 중단은 마지막 유효 상태 수신, 응답 지연은 요청 등록을 시작점으로 측정했다. 기준이 달라 평균을 직접 비교하지 않는다. 형식 오류 시간을 0초로 주장하지 않는다.

[측정 그래프 보기](experiment_charts.html)

## 8. 실험 결과 해석 (1분)

- 두 시간 측정치는 설정한 판정 기준 근처에서 나타났다.
- 15회는 PC 격리 실험이며 물리 네트워크 장애의 지연 분포를 대표하지 않는다.
- 형식 오류는 기록 시각의 해상도 때문에 탐지 소요 시간을 수치화하지 않았다.

## 9. RAG 점검 안내 흐름 (2분)

1. 규칙 엔진이 정한 장애 유형으로 해당 매뉴얼을 선택한다.
2. 매뉴얼의 절과 연결 로그를 Ollama에 전달한다.
3. 답변과 문서 제목·절·줄 위치를 함께 보여준다.
4. 근거 문서가 없으면 모델을 호출하지 않는다.

발표: 점검 안내는 가능한 원인과 확인 순서이며 실제 원인 확정이나 장치 제어가 아니다.

## 10. AI 응답 측정과 근거 검토 (1.5분)

- 동일한 형식 오류 이벤트 ID 77을 5번 호출했고 5번 모두 응답 생성에 성공했다.
- 응답 시간 평균 4.664초, 중앙값 3.638초, 범위 3.556~8.908초.
- 통합 테스트에서 한 답변의 매뉴얼·로그 일치를 검토했고, 초기의 근거 없는 시각 단정을 프롬프트 수정 후 재검증했다.
- 5개 응답 본문은 CSV에 없어 5건 전체의 근거 적합성은 아직 평가되지 않았다.
- 별도 재검증 한 건에서는 매뉴얼 밖의 권고가 남아 부분 적합으로 판정했다. 출처 표시는 문장별 정확성을 보증하지 않는다.

## 11. 실패 처리와 한계 (1분)

- Ollama를 사용할 수 없어도 장애 판정과 조회는 계속 작동한다.
- 근거 문서가 없으면 AI 점검 안내를 생성하지 않는다.
- 현재는 장치 한 대, PC 시뮬레이터, 제한된 실험 횟수로 검증했다.

## 12. 결론과 질의응답 (2분)

- 규칙 기반 감지, 이력 조회, 복구와 사용자 조치의 분리, 근거 문서 기반 점검 안내까지 연결했다.
- 다음 검증: 실제 Raspberry Pi 네트워크 단절 실험, AI 답변 5건의 문장별 근거 대조, 더 긴 운영 기간의 지표.
