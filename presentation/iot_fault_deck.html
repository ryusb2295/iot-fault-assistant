02

무엇을 점검했는지 남지 않는다

점검 과정과 최종 조치가 기록되지 않으면 다음 대응에 쓸 수 없다.

목표: 한 화면에서 끝나는 대응 흐름
1MQTT 메시지 수신

5사용자 점검과 조치 기록
해결하려는 문제는 두 가지입니다. 첫째, 장애가 나면 로그와 매뉴얼, 과거 사례를 따로 찾아야 합니다. 둘째, 점검한 내용이 기록으로 남지 않습니다. 그래서 목표는 오른쪽 다섯 단계를 하나의 웹앱에서 이어지게 만드는 것입니다. 수신, 판정, 기록, 근거 기반 안내, 조치 기록입니다. (약 1분)

// 장애 판정 3종

세 가지 장애를 서로 다른 신호로 잡는다

CONNECTION_TIMEOUT

상태 메시지 수신 중단

마지막 유효 상태 메시지 이후 10초 동안 다음 메시지가 없으면 판정

재현: --mode disconnect
RESPONSE_DELAY

요청 대비 응답 지연

서버 요청 후 3초 안에 응답이 오지 않으면 판정. 늦게라도 응답이 오면 복구로 기록

재현: --mode delay (4.2초 후 응답)
INVALID_MESSAGE

메시지 형식 오류

필수 필드(장치 ID, 상태값, 순번, 타임스탬프)가 없거나 JSON이 깨지면 판정

재현: --mode invalid
장애는 세 가지입니다. 첫째, 상태 메시지가 10초 동안 안 오면 통신 중단입니다. 둘째, 서버가 요청을 보냈는데 3초 안에 응답이 없으면 응답 지연입니다. 시뮬레이터는 일부러 4.2초 뒤에 응답하고, 그 응답이 도착하면 복구로 기록합니다. 셋째, 필수 필드가 빠졌거나 JSON이 깨진 메시지는 형식 오류입니다. 세 장애 모두 시뮬레이터의 모드 옵션으로 재현합니다. 같은 장애가 계속돼도 이벤트는 한 번만 등록되도록 중복 등록을 막았습니다. (약 1분 30초)

[여기서 브라우저로 전환] 시연은 통신 중단을 기준으로 합니다. 1) 대시보드에서 마지막 수신 시각이 2초마다 바뀌는 것을 보여줍니다. 2) 시뮬레이터 창에서 Ctrl+C로 멈춥니다. 10초를 기다리는 동안 "지금 Worker가 마지막 유효 메시지 이후 경과 시간을 0.25초마다 확인하고 있습니다"라고 설명합니다. 3) 장애 이력에 CONNECTION_TIMEOUT이 생기면 클릭합니다. 4) 로그, 매뉴얼, AI 안내와 출처를 보여주며 "AI는 원인을 확정하지 않는다"를 다시 말합니다. 5) 체크리스트 2~3개 체크, 조치 내용 입력, 저장. 6) 시뮬레이터를 --mode normal로 다시 실행하고 복구 시각이 찍히는 것을 보여줍니다. 시간이 남으면 --mode delay도 짧게. 문제가 생기면 바로 녹화 영상으로 넘어갑니다. // 응답 지연 이벤트, 실제 응답 1건을 매뉴얼·로그와 대조

답이 나왔다고 근거에 충실한 것은 아니다: 부분 적합

확인 항목판정근거
장애 유형과 문서 일치적합RESPONSE_DELAY에 response_delay.md의 네 절이 검색됨
매뉴얼에 있는 원인 후보대체로 적합처리 지연, CPU 부하, 재연결, 네트워크 지연, topic/request_id 불일치를 가능성으로 표현
로그에 없는 시각 단정개선프롬프트 수정 후 "마지막 정상 응답 시각" 단정이 사라짐
매뉴얼 밖의 원인과 점검부적합"소프트웨어 버그", "소프트웨어 업데이트 확인", "다른 네트워크에서 재시도"는 문서와 로그에 없음
출처 표시가 문장별 정확성을 보증하지는 않는다. 그래서 AI 안내를 확정 진단이나 자동 조치로 쓰지 않는다.
AI 답변이 근거를 잘 따르는지 실제 응답을 매뉴얼, 로그와 한 줄씩 대조했습니다. 문서 선택은 맞았고, 원인 후보도 대부분 매뉴얼 안에 있었습니다. 처음에는 로그에 없는 시각을 단정하는 문제가 있어서 프롬프트를 고쳤고 재검증에서 사라졌습니다. 그런데 소프트웨어 버그나 업데이트 확인처럼 매뉴얼에 없는 권고는 프롬프트로 금지해도 남았습니다. 그래서 결과를 부분 적합으로 판정했습니다. 이 때문에 AI 안내는 참고용이고, 판정과 복구는 규칙 엔진과 실제 로그로만 결정합니다. (약 1분 30초)
