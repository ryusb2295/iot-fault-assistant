# MQTT 상태 메시지 미수신 점검

장애 유형: CONNECTION_TIMEOUT

## 판정과 범위
규칙 엔진은 유효한 상태 메시지를 받은 뒤 10초 동안 다음 상태 메시지를 받지 못하면 CONNECTION_TIMEOUT을 기록한다. 이 기록만으로 장치 전원, 네트워크 또는 브로커 중 어느 곳이 원인인지 확정할 수 없다.

## 가능한 원인
장치 발행 프로세스 중단, 장치와 브로커 사이의 네트워크 단절, MQTT 브로커 중단, 잘못된 브로커 주소나 포트, 상태 topic 불일치가 가능한 원인이다. 로그와 현장 상태로 각각 확인해야 한다.

## 점검 순서
1. 장애 발생 시각과 마지막 유효 상태 메시지 시각을 비교한다.
2. Mosquitto 실행 상태와 `MQTT_HOST`, `MQTT_PORT` 접속 값을 확인한다.
3. `factory/RPI-01/status` 발행 및 구독 상태와 장치 네트워크 연결을 확인한다.
4. 장치 발행 프로세스와 전원을 확인한 뒤 상태 메시지 재수신 여부를 관찰한다.

## 관련 로그 예시
장애에 연결되는 대표 로그는 `factory/RPI-01/status` topic의 `TIMEOUT: 10초 이상 미수신`이다. 장치가 끊긴 뒤 이미 보낸 요청에 응답이 없으면 `factory/RPI-01/request` topic에 `NO_RESPONSE: 장치 통신 중단 중 (CONNECTION_TIMEOUT으로 판정)`이 남는다. 이 요청은 응답 지연이 아니라 통신 중단의 결과로 본다.

## 다른 장애와 구분
상태 메시지는 계속 들어오는데 요청에 대한 응답만 늦으면 RESPONSE_DELAY다. 메시지는 들어오지만 JSON이나 필수 필드가 잘못되면 INVALID_MESSAGE다. 브로커 연결이 끊긴 경우에는 시스템 상태에서 broker가 disconnected로 표시되고 장치 상태는 unknown이 되며 CONNECTION_TIMEOUT을 기록하지 않는다. 감시 Worker가 멈춘 경우에도 장치 고장으로 기록하지 않는다.

## 복구 판단
유효한 상태 메시지가 다시 수신되면 시스템이 복구 시각을 자동으로 기록한다. 복구는 메시지 수신 사실만 뜻하며 사용자 조치 완료와는 별도로 관리한다. 복구 후에도 상태 메시지가 2초 주기로 계속 들어오는지 1분 정도 관찰한다.

## 조치 기록 작성 요령
확인한 점검 항목, 원인으로 판단한 근거(로그 시각, 브로커와 장치 상태), 실제로 수행한 조치, 상태 메시지 재수신 시각을 적는다. 원인을 확인하지 못했다면 확인하지 못했다고 적는다. 이 기록은 같은 유형의 다음 장애 상세 화면에 이전 조치로 표시된다.

## 추가 확인
요청·응답 메시지가 계속 오는데 상태 메시지만 없다면 상태 발행 경로와 topic을 우선 확인한다. 모든 MQTT 메시지가 없다면 브로커와 네트워크를 함께 점검한다. 복구 여부는 실제 메시지 수신 기록으로 판단한다.
